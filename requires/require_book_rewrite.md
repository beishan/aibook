我建议把这个功能正式命名为“**书籍重写**”，内部则按“**重写项目 + 书籍新版本**”来建模。这样既符合你现在“同一本书生成新版本”的管理方式，也方便以后扩展原文对照、历史版本、AI 辅助重写、多人编辑等能力。

下面这版可以直接作为开发需求初稿。

# 书籍重写功能需求文档

## 1. 功能背景

现有书籍管理系统已经支持 TXT、EPUB 等格式书籍管理，并支持一本书存在多个版本、多个格式。

新增“书籍重写”功能，用于基于已有书籍内容创建一个新的可编辑版本。

重写过程中：

- 原书及原版本内容保持不变。
- 系统基于原版本创建一个新的书籍版本。
- 新版本拥有独立的章节、正文和元数据。
- 用户可以持续编辑、调整章节、增加或删除章节。
- 重写中的版本可以正常使用系统阅读器阅读。
- 重写完成后，该版本继续作为当前书籍的一个正常版本存在。

建议系统内部增加“重写项目”概念，用于记录：

原始版本 → 重写项目 → 重写后的新版本。

---

# 2. 核心原则

## 2.1 不修改原书

任何重写操作不得直接修改源版本。

创建重写时必须生成一个独立的新版本，并复制原版本的：

- 章节结构
- 章节标题
- 正文内容
- 书籍基础元数据
- 封面信息
- 作者信息
- 简介等信息

之后所有修改只作用于新版本。

---

## 2.2 保留版本来源关系

新版本必须记录来源：

```text
书籍
 ├─ 原始版本
 │   └─ TXT / EPUB / 结构化章节
 │
 └─ 重写版本
     ├─ 来源版本ID
     ├─ 重写项目ID
     └─ 当前重写状态
```

建议保存：

```text
sourceBookId
sourceBookVersionId
rewriteBookVersionId
rewriteProjectId
```

这样以后可以实现：

- 查看该版本来源
- 原文对照
- 内容差异比较
- 恢复原章节
- 基于同一原版本创建多个不同重写版本

# 8. 创建重写后的系统行为

用户点击：

**确认创建**

之后，系统需要在一个事务性业务流程中完成：

```text
1. 创建 RewriteProject
2. 创建新的 BookVersion
3. 记录 sourceBookVersionId
4. 复制书籍元数据
5. 复制章节结构
6. 复制章节内容
7. 建立原章节与新章节映射
8. 将新版本状态设置为“重写中”
9. 建立重写项目与新版本关系
```

成功后提示：

```text
重写版本创建成功

[开始重写]
[返回书籍详情]
```

点击“开始重写”进入：

```text
/rewrite/{rewriteProjectId}
```

# 53. 自动保存接口注意事项

建议章节增加：

```text
revision
```

例如：

```text
revision = 15
```

前端保存时：

```json
{
  "content": "...",
  "revision": 15
}
```

保存成功：

```json
{
  "revision": 16
}
```

如果服务器已经是：

```text
revision = 17
```

说明发生并发修改。

返回：

```text
409 Conflict
```

避免多个浏览器窗口互相覆盖正文。

# 54. 内容存储建议

正文内容不建议只保存复杂 HTML。

推荐：

```text
结构化富文本格式
+
生成后的HTML
```

或者至少限制 HTML 白名单。

避免编辑器生成大量：

```html
<span style="...">
```

导致以后 EPUB 转换异常。

如果你的书主要还是小说，我甚至更建议内部以：

```text
段落结构
```

为核心，而不是完全自由的 Word 式富文本。

# 59. 最重要的几个设计决定

整个功能开发时建议固定以下规则：

**第一，重写永远生成新版本，不修改源版本。**

**第二，新版本创建时必须将章节正文真正复制出来，而不是继续引用原版本正文。**

**第三，每个重写章节尽量保留 `sourceChapterId`，这是以后做原文对照、恢复、Diff 和 AI 重写最重要的数据基础。**

**第四，重写版本在“重写中”也属于正常 BookVersion，可以直接使用现有阅读器阅读。**

**第五，TXT、结构化章节是重写模块的标准输入，EPUB 等其他格式统一经过现有格式转换模块处理，不在重写模块里重复实现解析逻辑。**

**第六，重写编辑器的核心不是复杂排版，而是“章节管理 + 长文本编辑 + 原文对照 + 自动保存 + 历史恢复”。**

按照这个方向设计，后面即使增加“精校”“翻译”“AI 改写”“内容修复”等功能，也都可以复用同一套版本、章节和编辑器基础设施。

这里面我尤其建议你保留两个一开始可能觉得“不是必需”、但后面会非常值的设计：**`sourceChapterId` 原章节映射**和**章节级历史/快照**。这两个一旦最初的数据结构没留，后面再做原文对照、Diff、恢复、AI 改写会很难补；现在一起设计进去，实际开发成本并不会高很多。
