# 爬虫 Mihomo 节点管理

连接与备用组入口：系统设置 → **系统代理配置**。

执行器入口：系统设置 → **爬虫设置 → 执行器配置**。采集任务的队列执行器列表也可以直接跳转到对应执行器。

## 旧数据库升级

从旧版本升级时，数据库可能仍保留只允许 `DEFAULT`、`SELECTED` 的执行器代理模式约束，导致保存 Mihomo 执行器时报 `crawler_queue_executors_proxy_mode_check` 错误。

`1.45.143` 起，后端启动时会在事务中重建该约束，允许 `DEFAULT`、`SELECTED`、`MIHOMO`，保留已有执行器数据。重新构建并启动更新后的后端，再保存执行器即可；仅刷新前端不会修复数据库约束。迁移失败会使启动失败并回滚约束变更，需检查后端启动日志与数据库账户的表修改权限。

## 连接与启用

1. 新增系统代理，类型选择 **Mihomo**。旧代理自动按 **简单代理** 处理。
2. 填写实际 HTTP 代理地址、控制 API 地址（例如 `http://192.168.31.155:9111`）和密钥。实际采集入口不能填写控制 API 端口。
3. 点击“测试控制 API 与代理有效性”，分别验证控制器和代理出口；测试不切换节点。
4. 保存后点击“节点与备用组”，查看、搜索及检测全部具体节点。
5. 新增命名备用节点组，选择已有 Selector 受控组与对应 HTTP 入口，勾选并排序组内节点。此处保存的是应用内节点列表，不会在 Mihomo 中创建新的 Selector。
6. 在爬虫设置的“执行器配置”页选择队列，新增或编辑执行器，选择普通代理，或选择 Mihomo 系统代理及备用节点组。
7. 选择手动指定、仅故障自动切换、按时间、按章节或按任务数切换，设置阈值并保存。手动指定模式在下一次采集请求前应用所选节点。

密钥只保存在系统代理中，执行器不再复制密钥，运行时读取最新凭据；读取配置不会返回密钥，留空保留原值，勾选清除可移除密钥。

命名节点组绑定当前账户，执行器通过所属队列校验账户权限。系统代理沿用现有管理员共享资源的权限；停用、删除或改变代理类型后，引用执行器不接收新采集请求。Mihomo 资源不会混入普通爬虫代理池。

旧版直接配置在执行器上的 Mihomo 数据继续有效。在新执行器配置页点击“迁移到系统代理配置”，会建立系统代理与命名节点组并改为引用；迁移后可重新选择切换方式。切换普通代理模式仍保留该执行器的 Mihomo 配置。

已经绑定执行器的控制地址、受控组或入口不能直接改动，需先解除引用；节点列表、名称和密钥可调整。正在使用的节点组不能删除。不同节点列表若使用同一个 Mihomo 受控组，仍只能交给一个执行器管理。

执行器配置底部的“解除 Mihomo 引用”会释放受控组占用并将执行器改为默认代理，保留系统代理与备用节点组。仅切换普通代理模式会保留原引用与运行记录，需要释放节点组时请明确解除引用。

建议建立专用入口和代理组，避免改变其他应用的出口。将下面内容合并到现有 Mihomo 配置相应区块，机场提供者名称替换为实际值，不要覆盖现有配置：

```yaml
proxy-groups:
  - name: 爬虫专用
    type: select
    use:
      - 你的机场提供者名称

listeners:
  - name: crawler-http
    type: http
    listen: 0.0.0.0
    port: 7895
    proxy: 爬虫专用
```

后端和 Mihomo 在同一 Docker 网络时，代理地址通常为 `http://mihomo:7895`，其中 `mihomo` 替换为服务名。跨容器访问不能使用后端自身的 `localhost`。实际使用 IP 地址时需要相应端口可达。

应用不会自动修改 Mihomo 配置、更新机场订阅或清空全部代理连接。同一规范化控制地址与代理组只能由一个执行器管理；不同地址别名若指向同一个控制器，也应由用户保持代理组独立。本功能针对单实例后端，多个后端实例不能同时管理同一代理组。

## 自动切换规则

- 网站请求的网络连接失败也先在当前节点完成章节重试，再计一次节点异常并尝试用户勾选的备用节点；节点的延迟检测正常不代表它可以访问目标小说网站，不再因此阻止网站异常时的故障切换。
- 故障节点默认冷却 300 秒。全部节点不可用时任务进入等待，保留进度，每 30 秒允许下一次恢复尝试；冷却期内跳过故障节点。
- 控制 API 连接失败、鉴权失败、代理组不存在或切换结果无法确认时暂停该执行器，不能直接将全部节点判为失效。
- 执行器的 HTTP 401/403/429/451、源站 5xx、空页面、疑似网站验证页及配置中的正文失败特征按两层重试处理。同一章节在当前节点先请求 `max(2, 请求重试次数 + 1)` 次，全部仍异常才记一次节点异常；开启故障切换后，用下一个可用节点重试同一章节，一轮不重复尝试已耗尽重试的节点。正文待开放、普通 404、人工冻结、规则配置错误和 robots.txt 访问策略不会按正文反爬异常计入节点冻结。
- Mihomo 节点连续异常达到执行器的“连续节点异常阈值”后，按“异常节点冻结（秒）”冻结；节点计数及冻结原因持久化，成功采集清零该节点的连续异常，冻结到期自动恢复候选资格。默认阈值为 2，冻结 300 秒。普通代理使用网站连续失败阈值及代理冷却时长，计数以队列和代理为范围原子更新，避免并发请求丢失计数。
- 所有可用节点对当前章节重试耗尽但尚未全部冻结时，章节记录失败并保留诊断；全部节点冻结时任务等待，保留进度。执行器配置中可查看节点是否冻结、连续异常次数、原因及恢复时间；普通默认代理和指定代理同样展示状态。手动节点不能切换到仍冻结的节点。
- HTTP 429 的 Retry-After 会被遵守；等待超过内联重试上限时进入网站等待，本轮未完成重试不记节点异常。控制 API 错误仍独立处理，不能把控制器不可用误记为节点异常。
- 自动切换只使用所选具体节点，排除其他代理组、DIRECT、REJECT 等出口。节点改名或被移除后不会自动替换成未选节点。
- 手动切换与采集请求串行，切换前等待当前请求结束，切换后读取实际节点确认。托管请求结束时关闭其专属 Java HTTP 客户端，下一次请求创建新连接，避免复用旧节点隧道。

## 定期轮换

新界面明确选择一种切换方式，定期轮换需要至少两个节点。手动指定模式固定使用所选节点，章节重试耗尽后记录失败，节点冻结时等待，不自动换到备用节点。其他模式可独立启用故障切换。旧版配置在迁移前仍保持原组合触发逻辑。

| 条件 | 计数方式 |
| --- | --- |
| 时间 | 例如 300 秒。累计执行器采集请求、请求内限速等待及故障处理时间；不累计请求之间的解析、空闲、人工冻结和进程停机时间。最小非零间隔 30 秒。 |
| 章节 | 正文成功保存一次计数；同一任务和章节去重。失败重试、304、目录、待发布和失败特征不计数。 |
| 书籍任务 | 完整采集、正文补全、更新检查任务成功完成时计数；排除单章节任务、目录、元数据、导入和导出任务。 |

顺序轮换按节点组列表循环，随机轮换避免立即重复当前节点。成功切换或修改切换策略后重置时间、章节、任务等轮换计数；外部改变节点时，在下次采集核对并重置这些计数。按节点记录的连续章节异常计数会跨节点切换保留，只有该节点成功采集才清零。配置、节点组、冷却、去重记录、运行计数和最近 50 条节点事件保存在 PostgreSQL，重启后恢复。

人工冻结期间相应执行器不执行采集和节点切换，解除冻结后继续执行。系统代理的目录浏览、连接测试和节点检测仍属于独立管理操作。执行器运行状态面板可以查看最近确认节点、计数、等待原因与最近切换记录。

当前延迟检测使用 Mihomo 的单节点 `/delay` 接口，检测目标为 `https://www.gstatic.com/generate_204`；该结果不保证目标小说网站可访问。数据库表由项目现有 Hibernate `ddl-auto: update` 管理，无需新增数据库依赖。
